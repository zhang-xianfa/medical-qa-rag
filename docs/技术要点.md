# 技术要点与设计问答（医疗多轮问诊系统）

> 基于仓库当前代码整理（2026-10-02）。行号以 `backend/` 下文件为准。
> 本文件梳理系统实现的关键细节与设计决策，供快速了解实现全貌；运行部署见 README.md。

---

## 一、系统架构总览

```
浏览器 → nginx:443 (SSL) → /api/* → backend:8000 (FastAPI + gunicorn)
                          → /*     → frontend:80  (Vue3 静态文件)

LangGraph 工作流拓扑（graph.py）:
safety_check ──route_by_intent──> basic_interview (循环) ──> expert_interview (循环)
      │                                    │                        │
      └────────────── 红旗/非医疗 ─────────┴───────────────────────> response → [human_review] → END
```

技术栈：**DeepSeek（LLM） + LangGraph（Agent 编排） + FastAPI + PostgreSQL/pgvector（混合检索） + Vue3/Pinia/Tailwind（前端） + nginx（SSL/限流） + Docker Compose**。

设计主线：**「阶段式串行双通道问诊」** —— 先把"低成本收集信息"和"带知识库深挖"拆成两个显式的图节点，
而不是一个万能 prompt：

| 阶段 | 实现 | 知识库 | 终止条件 |
|------|------|--------|----------|
| safety_check | L0 正则 + PII 脱敏 + 合规审核 | 无（确定性规则） | 命中红旗 → 直接 response |
| basic_interview | 纯 Jinja2 prompt 模板，选择题式 | **不检索** | LLM 判 `next_action="assess"` 或 ≥ 5 轮 |
| expert_interview | prompt + **每轮同步检索 top-5** 注入知识 | 每次追问前检索 | 判 `assess` 或总轮次 ≥ 10 |
| response | DiagnosisAgent 综合历史+档案+知识 → 报告 | 检索结果最多 3 条×300 字 | 一次性输出 |

轮次配置在 `api/routers/messages.py:_detect_scenario`：`max_rounds=10, use_expert=True, basic_max_rounds=5`。

## 二、LangGraph 工作流细节

### State 与三种合并语义（state.py）

`MedicalQAState`（TypedDict）里不同字段用了**三种不同的 reducer**，这是理解状态流转的关键：

| 字段 | Reducer | 语义 |
|------|---------|------|
| `messages` | LangGraph 内置 `add_messages` | 追加式消息历史 |
| `search_results` / `collected_info` / `scenario_context` | **自研 `dict_merge`** | list 按 `knowledge_entry_id` 去重合并；dict 递归合并、新值覆盖旧值 |
| `round_count` 等标量 | 默认覆盖 | 新值直接替换 |

> 常见疑问：为什么不用内置 reducer？→ LangGraph 只提供 add_messages，
> 检索结果需要"多轮累计 + 去重"语义，直接覆盖会丢历史。

### 条件路由（routes.py，无状态纯函数）

- `route_by_intent`：红旗 → response；否则把最后一条用户消息交给 `RealRouterLLM.classify`
  （max_tokens=256, temperature=0.1, timeout=15s，独立于问诊 LLM —— ADR-014 的"路由与医疗 LLM 隔离"）。
- **防自说自话熔断**：`check_basic_interview_complete` / `check_expert_interview_complete` 里，
  如果当前阶段是 collect 但**最后一条消息是 assistant**（LLM 没有产生有效用户输入就自循环），
  直接路由到 response，防止空转。
- LLM 异常降级硬编码：`intent in ("diagnosis","follow_up") → basic_interview`，其余 → response。

### 诊断报告（diagnosis_agent.py + response_node.py）

- 输入拼装：检索结果 **最多 3 条 × 每条前 300 字** + 对话历史**最近 10 条** + 患者档案；
  `max_tokens=1024, temperature=0.3`，模板 `diagnosis.j2` **要求输出纯文本（严禁 JSON）**；
- 报告 JSON 字段：`primary_diagnosis{name,probability,rationale,certainty_level}` /
  `differential_diagnosis` / `risk_assessment{severity,urgency,warning_signs}` /
  `recommendations[]` / `red_flags[]` / `references[]` / `disclaimer`；
- `risk_assessment.severity` 枚举：轻度/中度/重度/危及生命；
- 安全措辞检查 `_check_safe`：负向断言正则拦「确诊/保证能会/肯定没问题」——只记 warning 不阻塞；
- 免责声明强制附加：所有诊断输出末尾必须有 `settings.DISCLAIMER_TEXT`。

## 三、安全护栏（确定性规则，不靠 prompt 工程）

### L0 过滤器（safety/l0_filter.py）—— 零 LLM 依赖

三条 CRITICAL 规则全部 **blocking 且不可恢复**，命中即中断整个工作流：

| 规则 | 关键词示例 | 专属响应 |
|------|-----------|----------|
| SUICIDE_INTENT | 自杀 / 不想活了 / 死了算了 / 喝农药 | 心理援助热线 **400-161-9995** |
| EMERGENCY_SIGNS | 胸痛 / 呼吸困难 / 大出血 / 抽搐 / 窒息 / 口唇发紫 | 3 步 120 急救指引 |
| OVERDOSE | 吃了 N 片药 / 喝了一瓶 / 过量服用 | 打 120 +「不要自行催吐」 |

另有 `NON_MEDICAL_PATTERNS`（如「怎么给乌龟洗澡」）识别非医疗输入：降级放行但标记 MEDIUM。

### PII 脱敏（safety/pii_detector.py）

6 种类型、正则带**前后断言防误伤**，**从后往前替换**避免位置偏移：

| 类型 | 正则要点 | 脱敏形式 |
|------|----------|----------|
| ID_CARD | `[1-9]\d{5}(19\|20)\d{2}(月日校验)\d{3}[\dXx]` | `[身份证号]` |
| PHONE_NUMBER | `1[3-9]\d{9}` | `[手机号]` |
| PERSON | 我叫/我是/患者：+ 2-4 汉字 | `[姓名]` |
| BANK_ACCOUNT | `62` 开头 16-19 位 | 前4+`****`+后4 |
| EMAIL / ADDRESS | … | 部分脱敏 |

双重防护：**前端 `piiMasker.ts` 预脱敏 + 后端 `safety_check_node` 脱敏回写 state**。

### 双向剂量阻断（safety/content_filter.py）

- 用户问「几片/剂量/多少毫克」→ 关键词拦截；
- 模型输出命中 `\d+\s*(mg|片|粒|ml|毫升…)` → 拦截并替换为「请咨询医生」；
- 即**问剂量拦、答剂量也拦**。

### safety_check_node 的一个 trick

LangGraph 的 `add_messages` 是「追加」语义，节点返回 dict 会产生新消息条目。
所以脱敏是**原地改写最后一条 user 消息的内容**（mutation 而不是 return），
因为 checkpointer 快照的是 mutation 之后的状态。—— 这个细节体现了对框架 reducer 语义的准确理解。

## 四、混合检索（knowledge/）

### 检索管线（retriever.py）

```
向量检索 top_k*2  +  关键词检索 top_k
        └────────── RRF (k=60) 融合 ──────────┘
        → authority/freshness 评分 → 按 knowledge_entry_id 去重 → 截断 top_k
```

- **RRF**：`score = 1/(k + rank + 1)`，两路同条目分数相加；
- **权威度是入库时预设的领域先验**（不是检索时 LLM 打分）：
  `guideline 0.9 > consensus 0.75 > textbook 0.6 > review 0.5 > case_report 0.2`；
- **新鲜度**：`base = max(0, 1 − (今年−出版年)/10)`（每年衰减 0.1），**超过 5 年再 ×0.7**；
  注释特意说明：老知识不一定没用，时效分只参与排序、不丢弃；
- **去重**：入库按 SHA256 内容指纹去重；检索按 `knowledge_entry_id` 去重；
- 查询构造：从主诉拼两条 query —— `"{主诉} 鉴别诊断 临床指南"` 和 `"{主诉} {伴随症状} 可能诊断"`。

### Embedding 三级降级（服务可用性优先）

1. 有 `EMBEDDING_API_KEY` → 阿里云 DashScope `text-embedding-v4`（1024 维，OpenAI 兼容协议）；
2. 无 key 或失败 → **本地 BGE-M3**（`FlagEmbedding.BGEM3FlagModel`，batch_size=8, max_length=512）；
3. 都失败 → 返回空列表，**RAG 整体跳过但对话不中断**（专家问诊降级为通用医学知识）。

### 向量存储（vector_store.py）

- 抽象接口 6 方法（create_collection/insert/search/update/delete/count），
  两个实现：`PGVectorStore`（余弦距离 `<=>`，`ON CONFLICT DO UPDATE` 幂等插入）与
  `InMemoryVectorStore`（dict + 手写余弦相似度）；
- 切换逻辑：`VECTOR_BACKEND=pgvector` 时用 PG，初始化失败**降级到缓存单例的内存库**；
- 表名做正则白名单校验防 SQL 注入。

## 五、LLM 层防护链（llm/real_llm_adapter.py）

「**LLM 永远不能把流程搞挂**」这条原则的实现细节：

1. **force_json**：业务输出全部要求 JSON，`_extract_json` 做**四重容错**：
   剥 ```json 围栏 → 正则取第一个 `{...}` 块 → 补缺失逗号（两轮正则）→ 剔除 None；
2. **Pydantic Schema 校验**：`L2ResponseSchema`（response_text/options/severity_assessment/
   is_emergency/next_action 等）、`ExtractedFacts`（儿科字段，`extra="allow"`）——校验失败走降级；
3. **prompt 泄露检测**：响应中含 `_SYSTEM_KEYWORDS`（"你是AI健康助手/禁止确诊/输出格式…"）
   → 判定为模型把 system prompt 吐出来了，返回空 dict 触发降级；
4. **重试策略**：MAX_RETRIES=3；429 退避 `2.0×(attempt+1)`s；**401/403 立即中止不重试**；
   其他错误 `0.5×(attempt+1)`s；
5. **兜底响应**：3 次耗尽 → 固定 5 选 1 选择题（疼痛/不适/肿胀/其他/说不太清楚）+
   `next_action="continue"` —— 特意**不从 prompt 里抽取用户原文**（防 prompt 泄露）；
6. 异常翻译靠字符串匹配（"timeout"→LLMTimeoutError 等），代码留 TODO 承认脆弱。

LLM 配置兼容三厂商（openai / deepseek / anthropic），统一走 OpenAI 协议 `base_url`。

## 六、持久化：状态不靠 LangGraph checkpointer

关键设计：**graph.compile() 没有传 checkpointer**，状态持久化是 API 层手工做的 DB 读写。

`session_store.save_state` 的原子 merge（最值得背的一段 SQL）：

```sql
INSERT INTO session_state (session_id, state_data, updated_at)
VALUES (:sid, :data, NOW())
ON CONFLICT (session_id) DO UPDATE
SET state_data = session_state.state_data || EXCLUDED.state_data, updated_at = NOW()
```

- PostgreSQL JSONB `||` 运算符做**浅合并**：新值覆盖同名 key，未传入 key 不动（幂等）；
- 局限：浅合并会整体覆盖嵌套 dict，靠 API 层先读全量再写回规避；
- 消息只在 `graph.ainvoke()` **成功后**才入库（失败不产生脏数据）；
- 表：`session_state(session_id, state_data JSONB)`、
  `messages(…, options JSONB DEFAULT '[]')`（选项卡片历史回显）、
  `medical_records`（诊断归档，version 每轮 +1）、`audit_logs`（6 个索引的审计日志）。

### 鉴权与安全细节

- 注册：SELECT 查重 + INSERT 在**同一事务**（防 TOCTOU），`IntegrityError` 兜底返回 409；
- 登录：**内存滑动窗口限流**（每手机号 5 次/300s → 429）；
  密码错误与用户不存在返回**同样的 401 文案**（防用户枚举）；
- JWT：HS256，payload `{sub: user_id, phone, exp}`，有效期 24h；
  所有会话/消息端点 `Depends(get_current_user)`。

## 七、API 与前端

### 消息发送流程（messages.py:send_message）

1. 每请求重新 `build_workflow()` 编译图（保证拿最新节点实现）；
2. `load_state` + `load_messages(limit=200)` 恢复累积状态 → 追加新用户消息；
3. 首轮注入用户档案（性别、按出生日期算年龄、身高体重、过敏史/慢病史/手术史/家族史）；
4. `await graph.ainvoke(state)` —— **当前是非流式**，整段工作流一次跑完；
5. 成功后依次持久化：用户消息 → save_state（白名单字段）→ assistant 消息（含 options）；
6. `next_action` 映射：`red_flag→emergency_interrupted`、`stage=diagnose→diagnosis_ready`、
   `done→completed`、否则 `continue`。

### SSE（占位实现）

- `GET /sessions/{id}/stream` 目前只发 heartbeat + 欢迎消息（协议已定义，实现是占位）；
- 协议定义了 6 种事件：`message / diagnosis_progress / diagnosis_complete / emergency / error / heartbeat`；
- 响应头三件套：`Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`
  （关 nginx 缓冲，防 SSE 攒批）。

### 前端要点（frontend/src/）

- Pinia 三 store（auth/session/message），组件不直接调 api/；
- **竞态保护**：`isLoading` 全局锁（禁切换/发送/删除）+ `AbortController` + requestSessionId 快照校验；
- `DiagnosisReport.vue` 用 **DOMPurify** 防 v-html XSS；`piiMasker.ts` 前端预脱敏。

## 八、部署（docker-compose.yml + nginx.conf）

- 4 服务：`db`（pgvector/pg16，healthcheck pg_isready）→ `backend`（depends_on healthy）
  + `frontend`（nginx 静态）+ `nginx`（80/443，挂载 certs）；
- nginx 限流：`limit_req_zone` 两个区域 —— `auth` 5r/m（`/api/auth/` burst=3）、
  `api` 30r/m（`/api/` burst=10 nodelay）；
- 6 个安全响应头：CSP / nosniff / X-Frame-Options DENY / X-XSS-Protection / Referrer-Policy / HSTS；
- SSE 关键配置：`proxy_buffering off` + `proxy_read_timeout 300s`；
- HTTP→HTTPS 301，TLS 1.2/1.3；后端 gunicorn 多 worker，非 root 运行。

## 十、设计问答（FAQ）

**Q：为什么不用 LangChain 的 Agent 而用 LangGraph？**
→ 医疗问诊需要**显式的阶段控制**（安全检测必须最先、问诊循环有轮次上限），
LangGraph 的 StateGraph 让流程是确定性的图拓扑，而不是 LLM 自由选工具的黑盒；
状态可持久化、节点可单独测试、条件路由是纯函数。

**Q：RAG 在这套系统里怎么用的？和"问一下答一下"的 RAG 有什么不同？**
→ 检索不是每次回答时做一次，而是**专家问诊阶段每轮追问前同步检索**，
把知识注入 prompt 帮 LLM 提出鉴别诊断级别的追问；最后由 DiagnosisAgent
综合「对话历史 + 患者档案 + 检索结果」生成报告。检索结果按 knowledge_entry_id
在 state 里跨轮次去重累计。

**Q：怎么防止 LLM 输出不符合格式把系统搞挂？**
→ force_json + 四重 JSON 修复 + Pydantic 校验 + prompt 泄露检测 + 3 次重试 +
结构化兜底选择题，任何一层失败都有降级路径（见第五节）。

**Q：医疗场景的安全怎么做？**
→ 三层：确定性 L0 正则（自杀/急诊/过量服药，零 LLM 依赖、不可恢复）；
PII 脱敏（前后端双重，6 类型正则带前后断言）；双向剂量阻断 +
报告措辞检查 + 强制免责声明。红线优先级高于一切 prompt。

**Q：状态怎么持久化的？**
→ 不用 LangGraph checkpointer，API 层手工 load/merge/save，
`save_state` 用 Postgres JSONB `||` 在一条 UPSERT 里做原子浅合并（见第六节）。

**Q：向量库为什么选 pgvector？**
→ 业务数据本来就在 PostgreSQL，向量存同库免去第二套存储的运维和一致性问题；
支持 ON CONFLICT 幂等更新；抽象接口支持内存后端降级（开发/无 DB 环境）。

## 十一、已知局限与演进点

1. `workflow/nodes/search_node.py` 存在但**未注册进图**——检索是 expert 节点内同步完成的，
   与 SDD 的"SearchAgent 异步并行"设计不一致；
2. SSE 接口是**占位实现**（协议已定义，未接流式生成）；
3. 两套 State 模型并存：实际跑的 TypedDict `MedicalQAState` vs 文档契约版 Pydantic `AgentState`；
4. 配置默认值多处不一致（`VECTOR_BACKEND` 的 memory/pgvector、`LLM_PROVIDER` 的 openai/deepseek、
   EmbeddingConfig 写的是 openai 参数但运行时走 aliyun）；
5. 关键词检索用 `[0.5]*dim` 均匀向量调向量接口的 hack（没有独立全文索引时的折中）；
6. SQLAlchemy models 的外键指向不存在的 `sessions` 表（实际表叫 `session_state`）；
7. L1 真实 LLM 路由未测试（测试走 `_MockRouterLLM` 关键词打分）；L2 PII 的地址 NER 未实现。

> 这些局限均有明确的原因分析与演进方向。如实记录当前边界，比掩盖问题更有利于系统演进。
